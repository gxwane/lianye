# 手动悬浮控制：独立评审与 V4 复核

2026-10-06。用户明确要求独立 agent 审查手动方案。三个 agent 未彼此沟通，各自读取原型、模型与截图，再由主 agent 整合；此为设计与实现审查，不是用户访谈，也不代表 Android 实机验证。

## 首次使用：manual_onboarding_review

初评指出授权后的下一步、滑动方向及首屏成功反馈缺失。建议待开始提示保持至点击开始；首屏成功后才显示已截数量；首次教学在接上新内容后收起。取消准备应直接可用，无需新增教程页和重复确认。

V4 复核实际查看待开始、首屏、接图后与窄屏截图：两行首次指导及常驻计数/结束的字量合适。指出桌面仅说“点开始”未说明按钮位置；已改为“打开要截的页面，用悬浮按钮开始”。正式实现不得依赖自动识别任意目标页面来显示悬浮球，原型示例与平台边界已记入设计。

## 过程反馈：manual_capture_feedback_review

初评要求首屏确认、有效新内容而非采样次数计数、接续失败即时可见、末段收尾及可移动控件；正常停留和回滑不弹提示。

V4 复核查看首屏、进度、缺口与 320 px 拖动截图，确认教学收起、计数与错误均可见且没有越界。发现首屏回调前点结束时旧代码主动确认首屏。主 agent 添加浏览器回归后确实失败；修正为结束只请求收尾，等待原回调后才生成结果。原回调失败则不生成草稿。第二次只读复核确认该必修项消除。接续失败时保留的计数配合持久警告表达有效前段；缺口恢复能力没有被承诺。

## 权限与恢复：manual_recovery_review

初评指出通知不可见时兜底失效、零有效画面不可虚构草稿、系统中断必须释放会话并保留有效内容。需要至少一种控制入口可用才进入准备后的目标页面。

V4 复核实际查看通知准备/进度、控制阻塞、中断截图，确认能力替换、失败重试与草稿保留。指出屏捕芯片具有系统停止共享含义，不能把它绘制成通知入口；悬浮授权也不应模拟成普通允许弹窗。已将芯片恢复为状态标记，整个状态栏明确模拟下拉；悬浮设置改为系统页面、开关及返回。第二次只读复核确认必修项解决。正式实现还需检查通知渠道可见性，原型能力标志不视为手机授权成功。

## 实施证据

- 六个新增模型边界：旧模型 12 通过 / 6 失败，修改后模型与 OEM 总计 25 通过。
- 首屏提前结束浏览器回归先失败，修正后原回归通过；首屏数量只由原回调确认。
- 通知面板底部漏出目标页先以截图观察，再以边界断言复现；屏幕高度从固定数值改为减去系统栏的剩余高度后通过。
- 最终 98 项原自动、77 项手动、10 项宿主检查及保存竞态回归通过，浏览器 0 JS 异常。
- 主 agent 实际查看最新总览、通知准备、控制阻塞、中断、窄屏拖动及深色状态截图。

所有图片、系统授权和导出仍模拟。真实屏幕采集、拼接算法、单 App 共享、悬浮窗排除、通知过渡过滤和真实末帧完整性尚未执行。
